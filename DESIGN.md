# monitor-hub: универсальный мониторинг серверов

Статус: версия 1.0.0. Готовы конфигурация `targets.toml`, движок проверки, CLI, демон
с расписанием и командами из беседы, служба systemd, TUI и проверка путей. Тип цели
`mail` (IMAP) отложен на следующую версию.

## 1. Зачем

Типовая задача: зайти на машину через PAM jump-хост, выполнить `ls -la` по папкам,
нарисовать картинку в стиле Midnight Commander и отправить её в беседу ВК. Для
каждой ВМ отличаются только учётка, пароль, папки, расписание и команда в беседе.
Поэтому цель описывается данными, а не кодом.

Цель: один демон и один список целей. Новая ВМ или папка - это блок в конфиге, а не
новый скрипт. Поверх - TUI, где цели видно, можно менять и запускать проверку.

Не цели (на первом этапе): веб-интерфейс, мониторинг метрик (CPU, диск), другие
мессенджеры, несколько пользователей с правами, запуск на нескольких серверах.

## 2. Общая картина

```
targets.toml  (цели: без паролей)        .env  (секреты и общий шлюз)
        \                                   /
         +-------> monitor-hub daemon <----+
                     |   |   |
         планировщик |   |   | команды из беседы ВК (long poll)
                     v   v   v
              PAM session (по одной на цель)
                     |
                     v
          ls -la -> разбор -> PNG (стиль MC) -> беседа ВК

TUI (Textual) <-- читает/пишет targets.toml, запускает проверки, смотрит лог и
                  статус демона. Сам мониторингом не занимается.
```

Ключевой принцип: демон и TUI - две независимые программы. Демон живёт под systemd
без экрана и не зависит от TUI. TUI можно закрыть, и мониторинг продолжится.

## 3. Конфигурация

### 3.1 `.env` - общее и секреты (права 600, в git не попадает)

```
PAM_HOST=...            # общий шлюз
PAM_PORT=2222
VK_TOKEN=...
VK_GROUP_ID=...
VK_PEER_ID=...          # беседа по умолчанию
ALLOWED_USERS=...       # кому можно команды
CRL_PAM_PASSWORD=...    # пароль каждой цели под своим именем
BK_PAM_PASSWORD=...
PGBK_PAM_PASSWORD=...
```

### 3.2 `targets.toml` - список целей (без паролей)

```toml
[defaults]
prompt_timeout = 120       # сколько ждать приглашение shell, секунды (минимум 30)
connect_retries = 2        # сколько раз пробовать сессию целиком
connect_retry_delay = 60   # пауза между такими попытками
stale_days = 0             # 0 = не отмечать устаревшие файлы
style = "backups"          # listing | backups | backups-sizes

[targets.crl]
title = "CRL"
pam_user = "..."
password_env = "CRL_PAM_PASSWORD"   # имя переменной в .env, не сам пароль
target_host = "..."
target_sel = 1
paths = ["/usr/local/ocsp/crl"]
style = "listing"
schedule = "daily 09:00"
command = "/get"

[targets.pgbackup]
title = "Postgres backup"
pam_user = "..."
password_env = "PGBK_PAM_PASSWORD"
target_host = "..."
paths = ["/mnt/bkp/backup_0", "/mnt/bkp"]
style = "backups-sizes"
sudo = true                          # sudo -n ls
schedule = "wed 10:00"
command = "/pgbackup"
peers = ["2000000002"]               # куда слать (по умолчанию VK_PEER_ID)
```

Правила:
- пароли только в `.env`; в `targets.toml` лишь имя переменной;
- у каждой цели своя учётка, ВМ, папки, расписание и команда;
- общий только PAM-шлюз (`PAM_HOST`, `PAM_PORT`);
- расписание: `daily HH:MM`, `mon HH:MM` (день недели), несколько через список
  (`schedule = ["wed 10:00", "fri 10:00"]`);
- время расписания - по часовому поясу машины, где работает демон;
- неизвестное поле или раздел - ошибка (опечатка не должна молча игнорироваться);
- имя команды `/name` уникально среди целей; `/targets`, `/run`, `/help` зарезервированы;
- в git кладётся только `targets.example.toml` с выдуманными значениями;
- валидация при старте и при сохранении из TUI: понятные сообщения, какая цель и
  какое поле неверны, до любого сетевого действия.

## 4. Устройство кода

Пакет `monitor/`:

| Модуль | Что делает | Статус |
|--------|-----------|--------|
| `common.py` | env-хелперы, `VkClient` с таймаутами и повторами | готов |
| `ls_report.py` | разбор ls, рендер MC-картинки | готов |
| `pam_session.py` | вход через PAM, Enter-nudge, повтор сессии | готов |
| `app.py` | .env, логи, общая схема проверки | готов |
| `config.py` | `targets.toml` и окружение: `Target`, `Schedule`, `Settings`, проверка | готов (этап 1) |
| `engine.py` | `Engine.check/run`: вход, ls по всем путям, картинки, отправка; стили отчёта | готов (этап 1) |
| `cli.py` | `monitor-hub validate`, `list`, `check <цель> [--no-send]` | готов (этап 1) |
| `daemon.py` | pid, логи, long poll | готов |
| `scheduler.py` | из `Target.schedule` строит задания (свой `schedule.Scheduler`, тег = имя цели) | готов (этап 2) |
| `router.py` | команда из беседы -> цель; `/targets`, `/run <имя>`, `/help`; права | готов (этап 2) |
| `hub.py` | демон: потоки целей, локи, сторож `run_timeout`, long poll, главный цикл | готов (этап 2) |
| `tui.py` | интерфейс Textual в стиле jmeter-reporter (см. раздел 5) | готов (этап 3) |
| `runlog.py` | итоги проверок и последний листинг каждой цели (для `status` и TUI) | готов |
| `envfile.py` | атомарная запись файлов, правка `.env` без потери остальных строк | готов |

Стили отчёта (поле `style`): `listing` (файлы и каталоги как есть, исполняемые со
звёздочкой), `backups` (папки как DIR, файлы по убыванию имени), `backups-sizes`
(то же, но у папок видны размеры в байтах). Различия - формат размера, цвета,
сортировка, слово в подписи.

Конфигурация читается в `config.py` и проверяется целиком до любого сетевого
действия: все ошибки списком, с указанием цели и поля.

Тип цели `mail` (проверка бэкапов по письмам IMAP) - в планах, в версию 1.0 не входит.

Изоляция целей: каждая цель отрабатывает в своём потоке с таймаутом, сбой или зависание
одной не останавливает остальные. Между входами на один шлюз небольшая пауза (шлюз
старый, не любит всплески). Одновременно не больше N входов (по умолчанию 2).

## 5. TUI (Textual)

Запуск: `monitor-hub tui`. Работает по ssh, мышь и клавиатура. Textual - необязательная
зависимость (`requirements-tui.txt`, как в проекте jmeter-reporter): без неё остаются
CLI и демон, а `monitor-hub tui` подсказывает, что поставить.

### 5.1 Вид (по образцу jmeter-reporter)

Тот же язык оформления, что у jmeter-reporter, чтобы два инструмента выглядели как один:

- Тёмная тема `claude-report`: фон `#1b1a19`, панели `#232120`, текст `#e6e1da`,
  акцент `#d97757` (оранжевый Claude Code), линии `#3d3a37`, приглушённый `#8b8b8b`,
  ok `#6fbf73`, предупреждение `#e5c07b`, ошибка `#e06c75`.
- Шапка в одну строку: `* monitor-hub   мониторинг серверов через PAM jump-хост`.
- Сверху поле-приглашение `>` в скруглённой рамке: путь, имя цели или команда
  (`crl`, `/run crl`); рамка становится акцентной, когда в ней фокус.
- Две колонки. Слева панель "цели" (таблица) и панель "параметры" выбранной цели.
  Справа "предпросмотр" картинки и "журнал". Панели с `border: round`, заголовок рамки
  приглушённый, при фокусе рамка и заголовок акцентные.
- Поля без рамок, плоские: подпись слева приглушённым цветом (`pam`, `вм`, `папки`, `tz`),
  поле на `surface-lighten`. Метки состояния в подписи: `+` найдено/ok (зелёный),
  `!` проблема (красный), `-` не используется (приглушённый).
- Только ASCII-значки: `+ ` и `- ` в дереве и списках, `*` у заголовков журнала, без эмодзи.
- Журнал `RichLog`: строки `- текст`, итог `* Готово` жирным в цвете статуса.
- Подсказки клавиш в нижней строке, приглушённым цветом.
- Горячие клавиши с `priority=True`, чтобы работали из любого поля:
  `ctrl+r` проверить без отправки, `ctrl+k` проверить и отправить в беседу, `ctrl+n`
  новая цель, `ctrl+s` сохранить, `ctrl+d` удалить (нажать дважды в течение 4 секунд),
  `ctrl+p` проверить пути, `ctrl+l` состояние демона, `ctrl+o` открыть последнюю
  картинку, `tab` дальше, `escape` вернуться в приглашение, `ctrl+q` выход.
- Заголовок окна терминала показывает, что делает программа (видно во вкладке):
  `[..] проверяю: crl`, `[ok] готово: crl`, `[!] ошибка: pg`; при выходе возвращается
  прежний заголовок.
- Все сетевые действия в потоках (`@work(thread=True, exclusive=True)`), интерфейс не
  блокируется; результат приходит через `call_from_thread`. Ошибка в файле или на ВМ не
  роняет программу, а попадает в журнал. Строки обычного лога (`logging`) тоже идут в журнал.
- Скриншот для README делает `tools/make_screenshot.py` через `run_test` и
  `export_screenshot` (SVG) на синтетических данных (`make screenshot`).

Эскиз:

```
* monitor-hub   мониторинг серверов через PAM jump-хост
+- > цель или команда --------------------------------------------+
| > crl                                                            |
+------------------------------------+-----------------------------+
| цели                               | предпросмотр                |
|  crl      CRL        ok   09:00    |  (последняя картинка)       |
|  pgbackup Postgres   !    wed 10:00|                             |
+------------------------------------+                             |
| параметры                          +-----------------------------+
|  pam +  вм 192.0.2.10  sel 1       | журнал                      |
|  папки  /var/example/reports       |  - вход на шлюз...          |
|  расписание daily 09:00            |  * Готово                   |
+------------------------------------+-----------------------------+
 ctrl+r проверить  ctrl+n новая  ctrl+s сохранить  ctrl+l лог  ctrl+q выход
```

### 5.2 Экраны и действия

1. **Цели** - таблица: имя, ВМ, папки, расписание, последний запуск, результат (ok /
   ошибка), возраст последнего отчёта. Enter - открыть, `ctrl+n` - добавить,
   `ctrl+d` - удалить, `ctrl+r` - проверить сейчас.
2. **Параметры цели** - форма: название, PAM-учётка, ВМ, пути, расписание, sudo, команда,
   стиль, получатели. Пароль вводится маскированным и пишется только в `.env`. Кнопка
   "Проверить подключение" проходит вход и показывает результат.
3. **Проверка путей** - пути человек вводит сам (по одному в строке). `ctrl+p` делает один
   вход на ВМ и для каждого пути отвечает: существует, это папка, есть право чтения,
   сколько записей. Результат рядом с каждым путём (ok / нет такого пути / не папка /
   нет прав / нужен sudo). Дерево каталогов не показывается и не кэшируется. Проверка в
   фоне, с отменой и таймаутом.
4. **Запуск сейчас** - выполняет проверку, показывает ход (вход, меню, shell, ls) в
   журнале, а справа последний листинг текстом в цветах отчёта. `ctrl+r` не отправляет
   ничего в ВК, `ctrl+k` отправляет, `ctrl+o` открывает последнюю картинку во внешнем
   просмотрщике.
5. **Статус** - `ctrl+l` показывает, запущен ли демон, его PID и последние итоги целей.
   Демон читает конфигурацию при старте, поэтому после правок нужен
   `monitor-hub restart`.

TUI не запускает мониторинг сам, пишет только `targets.toml` и `.env` (атомарно:
временный файл и rename, резервная копия предыдущей версии).

### 5.3 Тесты и устройство кода

- Модуль `monitor/tui.py` (приложение `HubApp`) с чистыми функциями отдельно от
  виджетов: форматирование строк таблицы, разбор ввода приглашения, значки состояния.
- Тесты через `App.run_test()` и `Pilot`, без реального терминала: выбор цели, форма,
  проверка ошибок ввода, запуск проверки с поддельным шлюзом, заголовок окна, ASCII-значки.

## 6. Безопасность

- Пароли не показываются в TUI, не пишутся в лог, в `targets.toml` и в сообщения
  об ошибках; в логе только имя переменной.
- `.env` и `targets.toml` проверяются на права (предупреждение при шире 600/640).
- Команды из беседы только от `ALLOWED_USERS` (пустой список - никому; всем - только
  явным `ALLOW_ANY_USER=1`); запуск `/run` по имени, а не произвольных
  команд. Пути проходят проверку на допустимые символы (как сейчас `SAFE_*_RE`),
  никакого подставления в shell без экранирования.
- Режим `sudo -n` только для целей с `sudo = true`; пароль sudo не запрашивается.
- Проверка ключа хоста: по умолчанию `accept-new`, `no` только явным выбором.
- Реальный `targets.toml` и `.env` в `.gitignore` и `.dockerignore` с первого дня.
  В публичный репозиторий идут только примеры с выдуманными адресами (TEST-NET,
  `example.org`).

## 7. Ввод в эксплуатацию

1. Скопировать `targets.example.toml` в `targets.toml`, `.env.example` в `.env`
   (`chmod 600 .env`), заполнить цели и пароли.
2. `monitor-hub validate` проверяет всё без сети: цели, пути, расписания, наличие
   паролей и настроек ВК.
3. `monitor-hub check <цель> --no-send` прогоняет цель вручную, сохраняет картинку и
   ничего не отправляет.
4. Первый боевой прогон: демон работает с тестовой беседой (`VK_PEER_ID` другой), отчёты
   сверяются с ожидаемыми.
5. Переключение на боевую беседу и запуск как службы systemd (`Restart=always`):
   `deploy/install.sh`.

## 8. Тестирование

Используется: поддельный PAM-шлюз на paramiko (настоящий `ssh` и `pexpect`), поддельный
ВК, Docker-матрица Python 3.10-3.13, ruff, mypy, bandit, покрытие не ниже 85%.

Уже есть:
- разбор и проверка `targets.toml`: хорошие и плохие файлы, по тесту на каждое поле;
- движок против поддельного шлюза: вход, все пути в одном сеансе, sudo, повтор после
  обрыва, Enter-nudge, неверный пароль без утечки секрета, отказ в доступе;
- картинки: формат, число страниц при длинных листингах, подписи;
- CLI: `validate`, `list`, `check`, коды возврата.

- планировщик и роутер: задания по целям, срабатывание в срок, права, ответы;
- демон: одна цель не идёт дважды, сбой одной не мешает другим, сторож времени,
  ограничитель входов на шлюз;
- сквозной: настоящий процесс `monitor-hub run`, ssh, поддельные шлюз и vk_api,
  команды из беседы -> картинки, SIGTERM убирает PID-файл;
- установщик systemd в режиме DRY_RUN.

- TUI: тесты Textual (`Pilot`) без реального терминала; окна на рабочем столе не
  открываются (`NO_OPEN_SCREENSHOT=1`), e2e с просмотрщиком только в Docker;
- проверка путей: настоящий `ssh` против поддельного шлюза и отдельно настоящий `bash`
  для самой команды проверки.

## 10. Риски и открытые вопросы

- Вход через PAM медленный и иногда зависает (приглашение не видно). Поэтому TUI
  не должен блокироваться: все сетевые действия в фоне, с отменой и таймаутом.
- У каждой ВМ свои причуды (sudo, права на папку, формат `ls`, меню PAM). Часть уйдёт
  в флаги цели; что не ложится в схему, получит запасной вариант `command` (своя команда
  вместо `ls -la`), но только для явных случаев.
- Проверка путей делает один вход на цель за раз (все пути в одном сеансе), поэтому
  шлюз не нагружается. Проверка запускается только по кнопке и при сохранении цели
  (по желанию), не в фоне.
- Путь вводится человеком, значит проверка должна отсеивать опасный ввод: допустимые
  символы, абсолютный путь, без подстановок shell (`;`, `$`, обратные кавычки).
  Проверка выполняется командой `test -d` / `ls -ld` с экранированным путём.
- Решить заранее: как хранить пароли. Простой вариант: `.env` с правами 600. Лучше:
  системное хранилище секретов (keyring) или `systemd-creds`, но это усложнит
  установку на VM.
- Репозиторий публиковать только с чистой историей (внутренние адреса не должны
  попадать в коммиты ни разу).

## 11. Принятые решения

1. Список целей в TOML, пароли отдельно в `.env` (имя переменной в `password_env`).
2. Репозиторий публикуется с чистой историей; лицензия PolyForm Noncommercial 1.0.0.
3. Сначала демон и конфиг, TUI после.
4. Типы целей: папки через `ls`; письма (IMAP) - позже.

## Дополнения v1.1

- **Типы целей.** `ls` (папки; вход `via = "pam"` или `"ssh"`) и `mail` (IMAP). Поля, не относящиеся к типу
  или способу входа, считаются ошибкой конфигурации, а не молча игнорируются.
- **Прямой ssh** использует тот же `PamSession` с флагом `direct`: пароль вводится при входе на машину,
  этапа шлюза нет. Ограничитель входов действует на каждый шлюз отдельно, для ssh не нужен.
- **Мессенджеры.** Протокол `Messenger` (`send_message`, `send_images`, `poll`, `label`), реализации `vk` и `telegram`,
  выбор через `MESSENGER`. Остальной код про конкретный мессенджер не знает.
- **Mail.** Письма берутся из IMAP за окно "ночи" проверяемой даты, имя машины и статус - из темы.
  Ожидаемые машины задаются по дням недели; отчёт - текст, сохраняется для предпросмотра в TUI.
- **Живой просмотр.** Не эмулятор терминала: пакетная команда повторяется в одном сеансе с маркерами начала и конца
  кадра, вывод очищается от управляющих последовательностей, секреты маскируются.
- **TUI и команды.** Описание полей и команд (`formspec.py`) общее для формы, строки `>` и проверки;
  правила видимости полей зависят от типа и способа входа.
- **Расписание.** Библиотека `schedule`: время по часовому поясу машины, пропущенные запуски не наверстываются.
  Принятое ограничение; для критичных задач запускайте демон как службу с перезапуском.
